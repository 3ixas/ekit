## Problem Statement

EKit has 92 active skills and keeps growing. Agents already pick owner skills from their descriptions, so routing works. What doesn't work is Elias's view of the collection: he keeps going back to the repository to work out which skill fits what he's about to do. The explicit-only workflows (`hill-climb`, `wayfinder`, `full-send`, `craft-review`, `modernize` and others) never run unless he names them, so the skill he doesn't remember is the one he loses. Multi-skill Workflow paths are recorded only as a prose table in the README.

## Solution

A new explicit-only skill, `which-skill`, in the `agent-system` group with role `either`. Elias asks "which skill should I use for X?", "is this thread using the right skill?", or "what changed since 2026-11-01?" and gets a Skill recommendation grounded in a generated Skill catalogue. The recommendation names one owner, why it fits, the supporting skills it brings in, the exact phrase to invoke it, where its authority stops, and any explicit-only skill worth naming. It then offers to start the owner and starts it only on his yes.

The catalogue is generated by `scripts/skills.py` from bundle metadata and new structured Workflow path data, and `check` fails when it is stale (ADR 0004). The same Workflow path data generates the README's workflow table, so there is one source.

Approved scope: `.scratch/which-skill/SCOPE.md` (2026-11-26). Terms: GLOSSARY.md (Skill recommendation, Workflow path, Skill catalogue).

## User Stories

1. As Elias, I want to describe what I'm about to do and get the skill that should own it, so that I don't have to search the repository.
2. As Elias, I want the recommendation to explain why that skill fits, so that I learn the distinction for next time.
3. As Elias, I want the exact phrase that invokes the owner, so that I learn the trigger wording and can say it directly later.
4. As Elias, I want the supporting skills the owner will bring in, so that I know what expertise is involved.
5. As Elias, I want the point where the owner's authority stops, so that I know what it will do without asking and what still needs my say-so.
6. As Elias, I want explicit-only workflows named when they really apply, so that I don't miss methods that never trigger on their own.
7. As Elias, I don't want explicit-only skills mentioned when they don't apply, so that the advice stays short.
8. As Elias, when a request could go two ways, I want both branches with the fact that decides between them, so that I can pick without a back-and-forth.
9. As Elias, I want a question only when neither branch is safe to start without my answer, so that I'm not interrogated for routine choices.
10. As Elias, when no skill fits, I want to be told plainly to ask normally, so that the nearest skill isn't stretched over my request.
11. As Elias, when an unmatched request looks recurring, I want `skill-review` suggested for a possible new skill, so that gaps in the collection surface.
12. As Elias, mid-task, I want to ask whether this thread is using the right skill, so that I can correct course early.
13. As Elias, mid-task, I want to hear about a skill I missed, judged from the current conversation, so that the remaining work uses the right method.
14. As Elias, I want to ask what changed since a date, so that I keep up with new and revised skills.
15. As Elias, I want "what changed" to work on a machine without the EKit checkout, so that the answer works in every host.
16. As Elias, I want "what changed" answers to say they are as fresh as the last sync, so that I don't mistake installed state for the repository's state.
17. As Elias, I want the advisor to offer to start the recommended owner, so that moving from advice to work is one word.
18. As Elias, I want nothing started without my yes, so that a recommendation never grants authority.
19. As Elias, I want an explicit-only workflow or anything with side effects to wait for my own words even after the offer, so that merges, sends and publishes stay under my control.
20. As Elias, I want `which-skill` to never trigger automatically, so that it never takes requests away from their real owners.
21. As Elias, I want only active skills recommended, so that I'm never pointed at candidate or paused work.
22. As Elias, I want the advisor to report when the host's loaded skills disagree with the catalogue, so that I notice a sync gap rather than receive advice about a skill that isn't installed.
23. As Elias, I want the README workflow table generated from the same Workflow path data as the catalogue, so that the two can't drift.
24. As the EKit maintainer, I want `check` to fail when the catalogue or README table is stale, so that a forgotten regeneration can't ship.
25. As the EKit maintainer, I want `check` to fail when a Workflow path names an unknown or inactive skill, so that retired skills don't linger in paths.
26. As the EKit maintainer, I want one command to regenerate the catalogue and README table, so that updating them is routine.
27. As the EKit maintainer, I want skills with side effects to declare their authority stop in metadata, so that the catalogue carries it from the source.
28. As the EKit maintainer, I want every explicit-only primary skill covered by a routing case, so that the eval exercises the advisor's main value.
29. As the EKit maintainer, I want a local opt-in eval that runs every routing case through `which-skill` in fresh Claude and Codex sessions, so that owner accuracy is proved by something other than the implementer.
30. As the EKit maintainer, I want that eval to skip cleanly when a CLI is absent, so that CI and other machines are unaffected.
31. As the EKit maintainer, I want the catalogue's token size reported, so that I notice when loading it becomes expensive.
32. As the EKit maintainer, I want `which-skill` projected to every host by the existing syncs, so that it behaves the same in Codex, Claude Code, OpenCode, T3 and Antigravity.

## Implementation Decisions

- **New skill bundle `which-skill`** in `skills/agent-system/`. Metadata: `origin` original, `invocation` explicit, `role` either, no upstream sources. Add a `SKILL.md` and `agents` files following the group's conventions, and add a row to the agent-system README and the activation manifest (active count 93).
- **Recommendation shape** (the skill's output contract):
  ```
  Owner: <skill>, <why it fits>
  Brings in: <supporting skills, or none>
  Say: "<exact invocation phrase>"
  Stops at: <authority stop>
  Also worth naming: <explicit-only skill and condition>   (only when it applies)
  ```
  Ambiguous request: at most two such blocks, each led by its deciding fact. No fit: one line saying no skill applies, plus a `skill-review` suggestion when the request looks recurring. "What changed since `<date>`": active skills whose added or reviewed date is on or after the date, grouped into added and revised, with a freshness note naming the catalogue's generation date.
- **Behaviour rules in SKILL.md:** advise, then offer to start the owner; start only on yes; explicit-only and side-effecting workflows still need Elias's explicit words. Recommend active skills only. Compare the host's loaded skill listing with the catalogue and report a mismatch instead of recommending a missing skill. Mid-task mode judges from the current conversation and names the current owner (if any) before recommending a change.
- **Workflow path data:** a new structured file under `config/` holding the Workflow paths now in the README "More workflows and when I use them" table. Each entry has a situation, an ordered list of steps, and optional notes. A step is a skill id, or free text for a non-skill step such as "release when authorized". The existing table's content migrates as is; wording changes are out of scope.
- **Metadata field `authority_stop`:** optional string, added to the metadata schema. Fill it for skills whose workflow can merge, publish, deploy, send, delete or change external state (expected to be about 20, including `implement`, `implement-ticket`, `implement-series`, `implement-parallel`, `full-send`, `full-stop`, `release`, `babysit-pr`, `modernize`, `email-assistant`, `planning`, `todoist-project`, `flowsavvy`, `flowsavvy-project`, `pr-feedback`). Take the wording from each skill's SKILL.md, not from invention. When it's absent, the catalogue says the skill has no external side effects and the recommendation states that the skill works locally.
- **Skill catalogue generator** in `scripts/skills.py`: renders a Markdown reference into the `which-skill` bundle listing every active skill (id, group, one-line purpose from the description, invocation, role, `authority_stop` if present, added date from the git history of its `SKILL.md`, `reviewed` date) and every Workflow path. It also renders the README workflow table between generated-section markers. The generator is deterministic: sorted, with no timestamps except a generation date taken from the latest commit date of its inputs, so regenerating unchanged inputs produces no diff.
- **CLI:** a new `skills.py catalog` subcommand that previews, and with `--apply` writes, the catalogue and README table. `check` gains staleness errors for both, plus validation that every Workflow path step id is an active skill.
- **Token size:** `capabilities` reports the catalogue's estimated token count, using the existing catalogue warning threshold.
- **Routing evals:** add 11 cases, one per explicit primary without a case: `full-send`, `full-stop`, `babysit-pr`, `modernize`, `security-audit`, `dogfood`, `planning`, `email-assistant`, `todoist-project`, `flowsavvy-project`, `flowsavvy-feature-request`. Each uses the existing fields with `explicit: true`.
- **Behavioural eval runner:** a local opt-in script that, for each routing case, runs a fresh non-interactive Claude and Codex session with `which-skill` invoked on the case's request, parses the `Owner` line, and reports pass/fail per case and host. Pass requires an exact owner match. For cases whose owner has an `authority_stop`, it also requires the `Stops at` line to name the labelled boundary (judged by keyword overlap with the case's `authority_stop`, with the failures listed for human review). It exits 0 with a skip message when a CLI is missing.
- **ADR 0004** governs the knowledge source; nothing here reads the repository live at answer time.

## Testing Decisions

- Good tests here check externally visible results: `check` errors and exit codes, generated file content, eval pass/fail. They don't check generator internals.
- **Seam 1, `check` (CI):** unit tests in the existing test suite build temporary repositories, following the existing fixture patterns, and assert:
  - a fresh repository passes;
  - an edited catalogue fails as stale;
  - a hand-edited README table fails as stale;
  - a Workflow path naming an unknown, candidate or paused skill fails;
  - a malformed `authority_stop` (empty or non-string) fails schema validation;
  - regenerating unchanged inputs is byte-identical.

  Extend the existing routing-scenario test so every explicit primary skill has at least one case.
- **Seam 2, behavioural eval (local, opt-in):** the runner above. Acceptance: every routing case matches its owner in both Claude and Codex, and the boundary check passes for side-effecting owners. Results are recorded in the PR's verification notes. Prior art: the opt-in real-browser tests and conditional Claude CLI plugin checks.
- **Fresh-session check:** one manual session in each of Claude and Codex confirms explicit-only invocation (the skill doesn't trigger on an ordinary request) and the recommendation shape.
- **Projection:** after merge, preview and apply all five host syncs and run all five doctors, per AGENTS.md.

## Out of Scope

- Automatic invocation, or any change to how other skills are selected.
- A general catalogue browser; the activation manifest keeps that job.
- Recommending candidate or paused skills.
- Rewording the README workflow paths beyond moving them into structured data.
- Requiring `authority_stop` on every skill.
- Running model calls in CI.

## Further Notes

- The added date requires git history at generation time, which is always available in the canonical checkout. Installed copies carry the generated dates.
- If the catalogue's token size crosses the warning threshold, split it into per-group references in a follow-up rather than trimming fields.
