# Skill admission rubric

A skill earns an active place only when it improves a recurring outcome enough to justify routing and maintenance.

For every proposed entrypoint, record:

- exact source repository, immutable revision, path, licence, and required assets;
- job to be done and realistic trigger phrases;
- current active owner and the useful behaviour that is missing;
- proposed disposition: import, adapt, merge, defer, pause, retire, or reject;
- invocation mode and why it will not steal unrelated requests;
- tools, other skills, private data, external services, and authority involved;
- maintenance burden and upstream-update strategy;
- positive, negative, and boundary scenarios needed to prove routing and behaviour.

Prefer merging a method into an existing owner when users would not benefit from choosing between two entrypoints. Preserve a separate skill when it has a distinct outcome, trigger, or operating contract. Popularity, length, and breadth are not evidence of usefulness.

For a large repository, inventory all entrypoints first, then assess by capability cluster. Do not conduct a long conversational review of each file. The final ledger must still account for every entrypoint.
