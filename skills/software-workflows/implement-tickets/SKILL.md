# Implement Tickets

Use when Elias requests Implement Tickets or explicitly requests sequential delivery of an identified, approved ticket graph. Ordinary language counts; a single-ticket or “next ticket” request alone does not select the sequence. Work on one ticket at a time in this run; do not dispatch tickets to parallel implementer subagents. A deliberate request for this workflow authorizes task-branch work, PR creation and updates, necessary review replies, CI reruns, PR auto-merge/queue management, and guarded merge for each ticket in that graph. It authorizes tracker updates needed to record those completed tickets under the configured workflow, not unrelated tracker changes, deployment, production operations, deletion of valuable data, paid actions or unrelated services. Higher-priority instructions and host approvals still apply.

1. Read the spec, complete ticket set, tracker configuration and repository instructions. Resolve the graph and its native or documented blocking edges from live tracker state, or local ticket files when configured. Record the graph boundary, ticket order and current outcomes. Do not infer a larger graph from an isolated ticket; if the graph or a consequential dependency is ambiguous, clarify before acting on it.
2. Refresh ticket and dependency state before each selection. A ticket is ready only when all its blockers are verified complete; an open PR, queued merge or armed auto-merge is not completion. Honour a stated order among ready tickets; otherwise choose a stable identifier order. Check existing PRs and actual merged changes before starting or resuming to avoid duplicate work. An issue's closed state alone is not proof of delivery: establish the configured completion evidence or report the ambiguity.
3. Start each ticket from the freshly verified target branch in a clean task branch or isolated worktree. Use the `implement` slice method to prove, review, fix and commit it, then use `full-send` as the supporting delivery method with the verified-merge endpoint. Its shared lifecycle and `babysit-pr` own PR monitoring, feedback, checks and all merge gates; never bypass required human approval or protection. Link the ticket using the configured closing mechanism. Reuse valid evidence for an existing PR rather than recreating it.
4. After a confirmed merge, verify the merged commit and required post-merge activation, reconcile the ticket's tracker state using the configured workflow, and refresh the target branch and graph before selecting another ticket. If another actor merged the PR, verify that its merged revision satisfies the ticket and required post-merge steps before treating it as complete. A closed unmerged PR or unknown outcome is a blocker, not completion.
5. If a ticket cannot proceed because of an unresolved decision, review gate, host access, external dependency or waiting budget, preserve its branch, PR, evidence and exact resume point. Request needed input without preventing independent progress when the host allows it. Continue other ready tickets only when their dependencies are complete and their work can be safely isolated from the blocked ticket. Do not duplicate a PR or run concurrent watchers for it. Revisit blocked tickets when new evidence resolves the blocker; stop when the graph is complete or no remaining ticket can safely proceed.
6. Report each ticket's verified merge and PR, or its waiting/blocked state, evidence and next action; distinguish incomplete dependent tickets from independent work. State whether auto-merge is armed. If the host cannot keep the turn alive or provide an authorized wakeup, say that the sequence has stopped and give the graph and PR state needed to resume. Auto-merge can finish one PR but does not by itself resume the sequence. Do not claim background monitoring or continuation without a real host facility.
