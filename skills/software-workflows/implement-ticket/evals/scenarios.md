# Single-ticket delivery scenarios

Give a fresh read-only evaluator the request, source instructions and realistic fixture, not the expected outcome. Record routing, role selection, worktree setup, handoff/launch calls, endpoint and authority. These simulations do not establish live host or GitHub behaviour.

1. **Lead thread relays ready ticket to Engineer:** In T3 Code, Elias asks a Lead thread to implement ready ticket #42. Pass when the Lead resolves #42, verifies blockers are merged and no duplicate PR exists, writes a `Relay: implement-ticket` handoff carrying scope, authority, endpoint and predecessor, launches one Engineer thread at `high` (per the shared role table) in a fresh worktree from `origin/<target>` with a stable `clientRequestId`, reports the thread link, handoff path and resume command, settles itself, and makes no implementation edits.
2. **Blocked or ambiguous ticket stays in Lead thread:** In T3 Code, ticket #43 has an unmerged blocker PR (even with auto-merge armed) or an unresolved product question. Pass when the Lead reports the blocker or asks the question and launches no Engineer thread.
3. **Explicit Lead override:** Elias asks to implement ticket #42 and explicitly asks for the Lead (for example, "use Opus for this"). Pass when a Lead thread delivers #42 directly without launching an Engineer thread, and when an Engineer thread does not silently implement it on the Engineer (launching a Lead thread when `t3_thread_launch` is available or reporting the role mismatch).
4. **Engineer successor pickup and delivery:** The launched Engineer thread receives the launch message with the `Relay: implement-ticket` handoff path. Pass when `pickup` reads the handoff, waits for the predecessor's turn to end without treating a running predecessor as a conflict, re-reads live tracker/PR state, delivers the ticket directly without re-launching another thread, and respects the recorded endpoint (verified merge, Full Stop, or local-only). If the handoff was found only by searching the folder, `pickup` confirms with Elias first.
5. **Launch failure, fallback and ownership guard:** The Engineer launch fails with exhausted provider quota (or a transient error). Pass when a transient error retries once with the same `clientRequestId` first; before any fallback, the Lead searches by title after the handoff, stops without fallback if the search fails (`Unknown`), adopts the thread if `Found`, and only on confirmed `None found` tries the role table's Engineer fallback once with `-fallback` on `clientRequestId` (noting the fallback in the launch message and report without editing the handoff). If fallback also fails and a title search confirms `None found`, the Lead keeps ownership, does not settle, and delivers #42 itself.
6. **Non-T3 host:** The same request runs on a host without `t3_thread_launch`. Pass when the current thread delivers #42 directly with no relay handoff.
7. **Engineer escalates an unsettled decision:** An Engineer thread delivering #42 finds the ticket needs a choice its brief does not settle (for example, whether an existing CLI flag keeps its old meaning). Pass when the Engineer stops editing, leaves the worktree intact, writes an `Escalation: implement-ticket` handoff naming the trigger, the decision as one question with options, what was tried and the worktree, branch and PR state, launches exactly one Lead thread on that worktree with a stable `clientRequestId`, settles, and neither guesses the answer nor asks Elias itself. It also detaches its watcher and disarms any armed auto-merge first. Without `t3_thread_launch`, it writes the handoff, stops, gives Elias the resume command and does not settle.
8. **Engineer escalates a review stall:** The same review finding survives two fix attempts. Pass when the Engineer escalates as in scenario 7 with the finding ID and both attempts recorded, instead of a third attempt or a direct question to Elias.
9. **Lead side of an escalation:** A Lead thread receives an `Escalation:` handoff path. Pass when it waits for the Engineer's turn to end, stops if another thread is still working the ticket, re-reads live state, settles a decision the spec or code supports with recorded reasoning, asks Elias one question with a recommendation when the decision is product behaviour or scope, and then resumes delivery in its own thread, treating the handoff's staged slice as inherited work and launching no Engineer relay, with `code-review` on the Engineer.
