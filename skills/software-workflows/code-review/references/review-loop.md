# Review-loop controls

Use when implementation or delivery owns repeated review and fixes. This reference controls the caller's loop, not the independent Standards/Spec reviewers' reporting axes.

Record the scope, fixed base and exact reviewed revision/diff. Keep a finding ledger with stable ID, axis, severity, evidence, disposition and proof. Reuse current valid review; do not add another coordinator or provider-specific review by default.

There is no fixed round count. Keep reviewing and fixing within the task's time allowance while the loop converges: the count of open confirmed actionable findings falls across rounds. Later rounds focus on changed behavior and open findings, with surrounding code needed to judge impact. Preserve both axes and earlier unresolved findings. Record a round limit only when the user sets one. Sharing this ledger across implementation and delivery keeps the convergence record intact at publication.

Verify each finding against the actual code, requirements, documented standards, actual callers and demonstrated consequences before acting on it. If a finding cites code, behaviour, or a requirement that does not exist or cannot be verified against the repository and spec, record it as rejected with the exact code or check evidence rather than acting on it. Rare does not mean optional for verified findings. Treat optional style/scope suggestions separately; an agent's disagreement alone cannot dismiss a verified finding. Keep the smallest sufficient fix. Evidence-backed dismissal of a verified finding needs the misread requirement/source or a check that refutes the claim.

After any behavior change, including instructions or meaningful conflict resolution, rerun affected proof and review the updated snapshot before claiming completion. A cosmetic edit that changes no behavior may stop without another round only when the caller's stricter snapshot rules allow it; `implement` still reviews every changed staged slice. Do not introduce a new change after final review without its required proof/review.

Stop when required proof passes and the final reviewed snapshot has no confirmed actionable finding. Optional nits alone do not block. If the same finding survives two fix attempts, a dismissed actionable finding returns, two successive rounds fail to reduce the confirmed actionable findings, a consequential scope decision is needed, or a user-set limit ends with required review/finding unresolved, report both sides and ask Elias. A stalled loop or a spent limit is never approval; leave the work unmerged and record the exact resume state.

For implemented slices, run each review and re-review round on the other role from the Roles section of the shared instructions (Lead for an Engineer-implemented slice; Engineer at High for a Lead-implemented slice), using fresh-context children without switching the caller's thread. If the other role's provider is unavailable, out of quota, would fall back to the implementer's own model/provider, or cross-role delegation is unavailable in the host/session, fall back to same-role review and record the fallback and reason. Report the actual reviewer role (and any same-role fallback) only when verified; do not claim cross-role coverage from same-role reviewers or add attribution boilerplate to commits/PRs.
