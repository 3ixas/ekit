# Implement Series

Use when Elias requests Implement Series or asks to deliver an identified, approved ticket graph sequentially or without specifying concurrency. Ordinary language counts; a single-ticket or “next ticket” request alone does not select the sequence. Work on one ticket at a time in this run; do not dispatch tickets to parallel implementer subagents. A deliberate request for this workflow authorizes task-branch work, PR creation and updates, necessary review replies, CI reruns, PR auto-merge/queue management, and guarded merge for each ticket in that graph unless Full Stop is requested. It authorizes tracker updates needed to record those completed tickets under the configured workflow, not unrelated tracker changes, deployment, production operations, deletion of valuable data, paid actions or unrelated services. Higher-priority instructions and host approvals still apply.

1. Read the spec, complete ticket set, tracker configuration and repository instructions. Resolve the graph and its native or documented blocking edges from live tracker state, or local ticket files when configured. Record the graph boundary, ticket order and current outcomes. Do not infer a larger graph from an isolated ticket; if the graph or a consequential dependency is ambiguous, clarify before acting on it.
2. Refresh ticket and dependency state before each selection. A ticket is ready only when all its blockers are verified complete; an open PR, queued merge or armed auto-merge is not completion. Honour a stated order among ready tickets; otherwise choose a stable identifier order. Check existing PRs and actual merged changes before starting or resuming to avoid duplicate work. An issue's closed state alone is not proof of delivery: establish the configured completion evidence or report the ambiguity.
3. Start each ticket from the freshly verified target branch in a clean task branch or isolated worktree. Use the `implement` slice method to prove, review, fix and commit it, then use the shared delivery lifecycle with the requested endpoint (verified merge by default, human merge for Full Stop). Its shared lifecycle and `babysit-pr` own PR monitoring, feedback, checks and all merge gates; never bypass required human approval or protection. Link the ticket using the configured closing mechanism. Reuse valid evidence for an existing PR rather than recreating it.
4. For the verified-merge endpoint, keep the current PR under one active owner until GitHub confirms its merge, a real blocker occurs, or the active waiting budget ends. CI and review events trigger a fresh PR-state read, but do not assume they include a merge event. Even when auto-merge is armed or `gh pr checks --watch` ends, keep the turn alive and check the exact PR state at bounded intervals (about 30 seconds, with backoff and rate limits) unless a real host mechanism guarantees a merge wake. Yield for user input and re-read head, base, reviews and checks when relevant; a failed read is not a merge. On confirmed merge, immediately verify the merged commit and required post-merge activation, reconcile the ticket's tracker state using the configured workflow, and refresh the target branch and graph before selecting another ticket. If required activation or completion evidence is blocked, do not start its dependants until resolved. If another actor merged the PR, verify that its merged revision satisfies the ticket and required post-merge steps before treating it as complete. A closed unmerged PR or unknown outcome is a blocker, not completion. With Full Stop, hand off ready PRs unmerged and continue safe independent tickets; their dependants remain blocked until an actual merge is verified, including on a later invocation.
5. If a ticket cannot proceed because of an unresolved decision, review gate, host access, external dependency or waiting budget, preserve its branch, PR, evidence and exact resume point. Request needed input without preventing independent progress when the host allows it. Continue other ready tickets only when their dependencies are complete and their work can be safely isolated from the blocked ticket. Do not duplicate a PR or run concurrent watchers for it. Revisit blocked tickets when new evidence resolves the blocker; stop when the graph is complete or no remaining ticket can safely proceed.
6. If the turn cannot remain active while a merge is pending, discover the current host’s actual continuation facility rather than assuming a specific harness. When supported and permitted by the current task and host, arrange one temporary, run-scoped wake or scheduled continuation for this same task; do not create duplicates or claim it exists until the host confirms it. Require host-enforced serialization or an atomic ownership claim so a wake cannot race an active run or another wake; if exclusivity cannot be established, do not create an unattended continuation. Give it the graph/spec pointer, exact repository and PR, endpoint, last verified head/base, evidence and blocker; on wake, re-read live state before acting and reuse the same ownership and merge gates. Preserve user-set total deadlines and all review/fix budgets across wakes; a per-turn waiting budget does not reset an explicit run-level deadline. Stop or remove the continuation when the graph completes, the user cancels, a run-level deadline expires, or a decision or other genuine blocker needs the user. On cancellation, inspect and report any armed auto-merge or queue state and act on it only within the cancellation instruction and existing authority. Full Stop never gains merge authority from a continuation. If the host has no permitted continuation facility or setup fails, report that the sequence has stopped and give the exact resume state; auto-merge alone cannot resume it. Report each ticket’s verified merge and PR, or its waiting/blocked state, evidence and next action, including whether auto-merge or a continuation is armed. Do not claim background monitoring without a real host facility.
