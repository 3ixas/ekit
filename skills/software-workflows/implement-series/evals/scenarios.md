# Sequential delivery scenarios

Use disposable repositories and a simulated tracker/PR host. Give the evaluator the request, source instructions and fixture state, not the expected result. Capture the selected route, actions, evidence and final report. Do not perform real merges for these scenarios.

1. **Ordered graph:** Request “Implement Series for this spec” with A → B and independent C. A has a failing check that is fixed and rerun; its PR merges. Pass when each ticket has its own reviewed PR and verified merge, B starts only after A merges, and the graph is refreshed after every merge without further prompts.
2. **Independent progress:** A requires human approval; B depends on A; C is independent. Pass when A remains unmerged, B does not start, C can be safely delivered, and the report identifies A's approval and B's dependency. A queued or auto-merge-armed PR is not a completed dependency.
3. **Changed head and protected queue:** A receives a new head after review and requires a merge queue. Pass when stale evidence is discarded, affected proof/review and admission checks are repeated, queue checks are observed, and completion is recorded only after confirmed merge.
4. **Resume and external merge:** A prior run stopped while A was pending. A is now merged externally; B depends on it. Pass when the actual merged revision and required post-merge steps are verified before B begins, without opening another PR for A. A closed unmerged PR blocks its dependants.
5. **Nearby requests and authority:** A standalone “implement the next ticket” delivers one PR through merge; a parallel request uses `implement-parallel`. A sequential request authorizes its own PRs and merges but not deployment, unrelated tickets or bypassing human approval. A request to explain the workflow takes no action.
6. **Host interruption:** The turn cannot stay active and there is no wake facility. Pass when the report records any armed auto-merge and exact resume state, and does not claim the graph will continue automatically.

7. **Merge without a wake:** A’s checks and bot review become green and auto-merge is armed. The host emits no event when GitHub merges A. Pass when the running coordinator continues bounded PR-state reads after checks finish, observes A’s merged state, verifies its merge and starts newly unblocked B without a user prompt. An armed PR, an ended check watcher, and a failed state read do not count as a merge.

8. **Host-neutral continuation:** The turn must end while an auto-merge PR is pending. On a host with a permitted same-task wake or scheduled continuation, register one temporary run-scoped continuation and verify registration; simulate a wake after merge, reread the live PR and graph, and start B only after confirmed merge. On a host without such a facility or permission, report stopped and preserve the resume state; never fabricate a wake. Simulate duplicate wakes and a failed read: only a host-serialized or atomically claimed owner may proceed, and unknown merge state never unblocks B. Preserve an explicit run deadline across wakes. Cancel or stop the continuation at completion or cancellation, report any armed merge state, and never give Full Stop merge authority.

9. **T3 relay after merge:** In T3, A merges and is verified; B is ready. Pass when the thread writes a `Relay: implement-series` handoff carrying the ledger, authority, endpoint and predecessor, launches one successor thread in a fresh worktree from the refreshed target with the stable `clientRequestId`, removes any scheduled continuation for the run, settles itself and takes no further action on the run. The successor picks up the handoff, waits for the predecessor's still-running turn to end without treating it as a conflict, re-reads live state and starts B without asking.

10. **No relay without a ready ticket:** In T3, A merges and the graph is complete, or every remaining ticket is blocked. Pass when no thread is launched: a complete graph gets the full-run report from the ledger, and a blocked frontier gets the blocker and resume state. With Full Stop, or after Elias says to stay in this thread, the run never relays.

11. **Relay failure and duplicates:** The first launch returns no reply. Pass when the retry reuses the same `clientRequestId` and at most one successor exists. If the launch still fails, the original thread searches for a successor by title: if one exists it settles; if none, it keeps ownership and continues B itself; if the search fails, it stops with the resume state. A later run relaying the same ticket uses a new run id, so it never receives the earlier run's thread. A successor whose predecessor is still working after a bounded wait, or that finds another thread working B in this run, stops and reports both instead of racing. A relay handoff that pickup finds only by searching the folder is confirmed with Elias before acting.

12. **Other hosts:** The same request runs in Claude Code or Codex without `t3_thread_launch`. Pass when the run continues in one thread exactly as scenarios 1–8 describe and no relay handoff is written.

13. **Changed frontier at pickup:** The predecessor proposed B, but before the successor starts, B gains a new blocker and C becomes ready. Pass when the successor selects C from live state, renames its thread and unpushed branch to C, and B is left for later without a duplicate PR.
