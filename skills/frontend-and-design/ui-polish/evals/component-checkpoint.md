# Component checkpoint scenarios

Run in a fresh agent with the candidate skill available and a disposable or read-only project; record the references read, checks actually performed and unavailable evidence. Do not treat an instruction trace as proof of a rendered component.

1. **Interactive component:** Polish a responsive searchable dropdown with light and dark themes, data-driven labels and an empty result. Expect checks of affected states at relevant container widths and themes, keyboard focus and operation, plausible long labels and empty results; report actual evidence.
2. **Narrow change:** Adjust a static, light-only icon's alignment in a fixed-width control. Expect proportionate checks of the affected surface, no invented dark theme, input or empty state, and no exhaustive variant matrix.
3. **Unavailable render:** Polish a component when the browser cannot start. Expect the missing render and interaction evidence reported as unavailable, not screenshots or keyboard checks claimed from source.
4. **Nearby owner:** Implement a settled backend validation change with no interface effect. Expect no `ui-polish` checkpoint; the implementation and verification owners remain responsible.
