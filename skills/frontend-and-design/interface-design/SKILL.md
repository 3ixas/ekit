# Interface Design

## Outcome

A user-approved, reference-led interface direction with a durable `DESIGN.md`, a coherent screen exploration, and an implementation inspected on its real surface.

## Choose the path

Run the complete orchestration for a new product surface, a new visual direction, or a substantial redesign. A small settled consistency change may use the existing product and design system directly; do not open an exploration loop when the decision is already clear. An existing coherent interface that only needs craft belongs to `ui-polish`.

## Orchestration

Load `grilling` and use its collaborative exploration during open design decisions. Explain why consequential choices about journeys, hierarchy, density, layout, or interaction matter, adapting to the user's understanding. Use concrete flows, reference comparisons, visual alternatives, or a targeted prototype to make the trade-offs inspectable; develop the reasoning behind the user's response into the next iteration. Treat aesthetic agreement and usability evidence separately. Keep this within the existing exploration and sign-off checkpoints, with a brief reusable-thinking reflection at sign-off; small settled changes still skip exploration. Unsettled product behavior and information architecture retain the owner named in Boundaries.

1. **Frame the work.** Establish the product or feature, audience, primary job, platform, constraints, target surfaces, and what success means. For an existing product, inspect the current implementation and rendered surface before proposing a replacement direction. For a redesign, record what must survive using [redesign preservation](references/redesign-preservation.md); carry its checks into the implementation handoff.
2. **Choose the design branch.** For substantial websites and web-app surfaces, use the [Taste toolkit](references/taste-toolkit.md): websites start with a subject inventory, section claims/proof, honest asset plan and competitor-specific concept; app screens start with their main question, important finding, next action and representative data that reconciles. Use the direction generator to broaden the existing options round, then carry the chosen decisions into `DESIGN.md`. Small settled changes keep the existing direction and skip drawing.
3. **Build a reference set.** Combine references supplied by the user with carefully selected external examples when needed. Give each reference a job: flow or information architecture, layout and hierarchy, typography and colour, component behaviour, imagery, or motion. For a web motion reference when useful, consult `motion` and its Subframe Motion guide. For a substantial new surface or redesign, when a reference library tool such as Mobbin or Refero is connected, run one focused search per reference job and record each result's source and query; without one, say so and use supplied and manual references. Record why each reference fits and what must not be copied. Do not average incompatible references into a generic result.
4. **Extract design direction.** Derive the transferable design DNA: content priority, geometry, rhythm, density, typography roles, semantic colour roles, surfaces, components, states, responsive changes, motion purpose, and platform assumptions. For an open or consequential direction, run an options round (`grilling`'s options rounds): three coherent directions shown side by side as quick visual sketches, each diverging on a named axis and naming the references it draws on, one of them a stretch, with a recommendation. Develop the chosen direction; Elias can combine or reject all. Choose a distinctive signature and explicit anti-goals; do not spend freedom on familiar AI defaults.
5. **Write or update `DESIGN.md`.** Record the product decision, scope, references, chosen direction, signature, anti-goals, semantic tokens with rationale, one icon family, interface copy rules, content and brand-asset requirements, screen and state matrix, responsive behaviour, accessibility and motion requirements, acceptance criteria, open decisions, and the exploration record. Read [design contract](references/design-contract.md).
6. **Choose the exploration surface and run its checkpoint.** For substantial new direction, explore screens before implementation. If the project's `DESIGN.md` already records an exploration service, keep using it so the work stays in one place. Otherwise use Claude Design when the host offers the Design artifact type, then Google Stitch when its tools are connected. If the user names a service, use that one. Follow the matching loop: [Claude Design loop](references/claude-design-loop.md) or [Stitch loop](references/stitch-loop.md). Before any external write, tell the user what will be created or updated and obtain confirmation unless the current request already authorizes that specific write. If neither service is available or exploration is deliberately skipped, record the reason in `DESIGN.md`.
7. **Explore and iterate.** Build the design system from the approved `DESIGN.md`, generate representative screens from real content and journeys, and run a second options round on the key screen: three versions of the hero screen in the chosen direction, side by side. After that, run further options rounds only when a new taste decision comes up. Compare against the references, requirements, states, responsive targets, and accessibility needs. Make focused edits one material change at a time and keep the exploration record current. Prompt the generator as [generator prompting](references/generator-prompting.md) describes: for a redesign, reproduce the current screen before varying it; describe structure rather than adjectives; refine the selected direction instead of branching; fix exact defects by direct edit; and render the product's real logo and identity assets.
8. **Obtain sign-off.** Do not treat a generated screen as the product decision. Before asking for approval, run a distinctiveness check: could these screens belong to any AI-built app (ask the questions in [AI-default patterns](references/ai-default-patterns.md)), is the recorded signature visible on every key screen, and does anything break a recorded anti-goal? Then critique the screens as rendered, not their source, using [screenshot critique](references/screenshot-critique.md): capture desktop, tablet, and phone widths, run its passes (preferably through a fresh-context reviewer), and fix the three largest problems for at most three rounds. Respect the exploration host’s rendering restrictions: obtain any required permission and record unavailable captures as verification gaps. User-reviewed artboards establish user feedback, not a self-performed rendered check. Fix what fails before presenting. Present the selected direction and its remaining trade-offs; record the user's approval, rejected alternatives, open decisions, and links to the approved screens or screenshots in `DESIGN.md`. If the direction changes materially, update the document and repeat the relevant exploration.
9. **Hand off and verify.** Carry the approved tokens, hierarchy, states, content rules, and interaction behaviour into project-owned components. Use `implement` for delivery and relevant specialists for technical guidance. Once `DESIGN.md` is approved, add a one-line pointer in the project's `AGENTS.md` or `CLAUDE.md` telling UI work to read it (a pointer, not an import of the whole file). Use `verify` on the real rendered interface at representative sizes and states, checking hierarchy, geometry, content realism, keyboard focus, accessibility, responsive behaviour, motion reduction, and visual parity with the approved direction. For a web surface used on phones, include `ui-polish`'s mobile-web mode, which covers safe areas and the colours behind mobile Safari's bars. Exploration output is design evidence, not production code by default.

Taste supplies strong design defaults, with the approved project contract taking precedence. Its scripts, source references and libraries are conditional supporting tools; no separate Taste entrypoint or comparison-build stage is added.

Read [reference-led design](references/reference-led-design.md) for the reference and direction method. Read [reference sources](references/reference-sources.md) when the user has not supplied enough examples, asks for components to adapt, or a reference library tool is connected. Read [design contract](references/design-contract.md) when creating or reviewing a project `DESIGN.md`.

## Boundaries

Unsettled product behaviour or information architecture routes to `grill-with-docs`; a known destination with an uncertain route may need `wayfinder`. Use `prototype` when one isolated throwaway experiment is the fastest way to answer a consequential design question. Exploration screens are evidence, not production source code or a replacement for project-owned components. `DESIGN.md` stays canonical; a service's own design system follows it. Do not invent a visual direction from generic AI habits, generic placeholder content, or a mood board with no product purpose.
