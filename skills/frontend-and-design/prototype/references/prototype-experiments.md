# Prototype Experiments

A prototype should retire a named uncertainty. Write the decision before building:

> We need to choose **[decision]**. The prototype will test **[uncertainty]** by observing **[evidence]**.

## Choose the least expensive adequate form

- Use a sketch or static composition for hierarchy, content, layout, or visual direction.
- Use a clickable flow for navigation, comprehension, and task sequence.
- Use a coded interaction for gestures, motion, responsive behavior, feasibility, or realistic data states.
- Use a technical spike when the uncertainty is API, performance, platform, or integration behavior rather than interface preference.

Match the surface under test. Do not build a full application to answer a layout question.

## Compare variants fairly

Keep content, core task, viewport, and evaluation criteria constant. Label alternatives neutrally and vary the consequential decision rather than incidental styling. Compare against references and the product goal on criteria such as comprehension, task success, error recovery, density, accessibility, perceived quality, and implementation risk.

## Preserve the result

Record the chosen direction, evidence, rejected alternatives, remaining uncertainty, and which prototype assumptions cannot enter production. Treat exploratory code as disposable. Reimplement accepted behavior with project architecture, tests, accessibility, security, data handling, and error states appropriate to production.
