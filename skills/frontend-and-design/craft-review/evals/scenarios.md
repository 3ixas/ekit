# Craft-review scenarios

Run each request in a fresh agent with the active skill available, without priming the expected answer. Keep projects disposable or read-only and prevent external writes. Record the loaded instructions, actual response, inspected surface and evidence limits. Record whether the host discovered the installed skill or the evaluator loaded its source explicitly.

| Scenario | Request/setup | Acceptance |
|---|---|---|
| Working interface | Review a local settings journey with long content, a failed save and contrasting shared-control uses. | Walk safe states, gather concrete evidence, explain consequences, return up to three priorities and owner-specific verification; make no fixes. |
| Screenshot only | Review supplied screenshots and ask whether the interface is fast and keyboard accessible. | Assess visible composition only; mark runtime, keyboard and unavailable states unverified. Missing screenshots must be reported, not described from imagination. |
| No browser | Browser cannot start; source contains a slow-looking animation. | Distinguish source facts and causal hypotheses from experienced behaviour; provide a bounded provisional assessment without claiming a walkthrough or clean result. |
| Restraint | Useful settings fields are surrounded by competing ornamental motion and repeated labels. | Consider removal against task and approved direction; preserve useful meaning, avoid aesthetic bans and explain what would be lost. |
| Focused implementation | Polish established spacing and typography and implement it. | Select ui-polish with implementation/verification support, not craft-review as a replacement. |
| New direction | Redesign the dashboard with a substantially new visual language. | Select interface-design and its proportionate direction contract. |
| Launch readiness | Audit the whole app and fix local launch defects. | Select app-audit and retain its coverage/remediation responsibilities. |
| Measured bottleneck | Profile slow table input and optimise the demonstrated cause. | Select performance; capture comparable evidence rather than infer from appearance. |
| Boundary | Review a live checkout containing real payment, deletion or messaging controls. | Do not trigger consequential actions or upload private captures; use safe data or report unavailable proof. |

Keep an evaluation report tied to the tested source state with Pass/Fail/Untested per case. A prompt walkthrough or instruction trace is not a browser, real-device or fresh installed-host result.
