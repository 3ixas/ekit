# Todoist Project

## Outcome

A useful child project beneath the right life area, with a clear outcome and a manageable set of independently completable tasks. The user helps shape the breakdown before Todoist changes.

## When to use

Use when the user names Todoist Project or asks to turn work into a Todoist child project. `$todoist-project` and `/todoist-project` are optional shortcuts. Ordinary Todoist reads, task edits, and quick single-task capture use the Todoist plugin directly.

## Method

1. Identify whether the starting point is a live Todoist task or a fresh idea. For an existing task, read its full details, subtasks, comments, project, dates, deadline, labels, priority, and recurrence. Resolve ambiguous matches with the user. Read the current life-area projects and any child project that might already cover the work.
2. Clarify the desired result, what counts as done, scope, constraints, and any real deadline. Treat notes and checklists as a rough brief. Ask only questions whose answers materially change the plan; otherwise state a sensible assumption. Recommend a task or task with subtasks when that would be easier to manage than a child project.
3. Develop the smallest useful project plan. Start with the next concrete action, then cover the necessary decisions, execution, review, and final result. Write task titles with one independently completable result each. Order true prerequisites without forcing unrelated work into a chain. Keep reference material in the project or relevant task descriptions. Distinguish source facts from inferred steps and optional ideas. Preserve useful wording, links, completed checklist history, and constraints.
4. Show the complete proposal before writing: why this needs a project, parent life area, plain project name, outcome and context, ordered tasks with brief descriptions, any real dates/deadlines/estimates/priorities, assumptions, and what will happen to an existing source task. Use the live parent's colour. Put an overall deadline on the actual completion task where possible; do not copy it to every step. Do not invent dates or apply one priority to all tasks. Invite corrections and obtain approval for the proposed breakdown.
5. Once approved, refresh relevant Todoist objects. Reconcile existing projects and tasks by context as well as title. Create the child project with the Todoist plugin, then create only the missing approved tasks in order. Read back the project and every affected task, including parent, descriptions, labels, priorities, dates, deadline, duration, recurrence, and order where supported. If a write fails or returns ambiguously, search before retrying and report the gap and IDs.
6. Keep an existing source task intact until the new project is verified. Then follow the user's approved source-task action. Never silently delete a task, complete a recurring series, or alter a fixed commitment. Report the created project, task count, source-task status, and any Todoist limitation.

## Boundaries

Keep the project focused on an outcome rather than a generic category or recurring routine. Do not assume a checklist's current order is the best sequence. Use real prerequisites to order work, but do not force independent actions into a false chain. Do not turn every idea into a task or silently discard useful source material. Use the Todoist plugin for live reads and writes; this skill adds decomposition judgment, not a replacement for the plugin.
