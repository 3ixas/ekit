# Review and actions

## Coverage and existing organisation

Discover connected personal accounts and verify their identities before reads or writes. The supplied workflow covers Main and Other personal Gmail accounts; use live account metadata and current user context rather than embedding addresses or link IDs in the skill. If an identity is ambiguous, ask only for the account choice needed. An inaccessible account is unreviewed, never empty.

Use live label totals for Inbox counts, distinguishing messages, threads, and unread counts. Do not treat search estimates or a page length as an exact total. Retrieve read and unread mail, deduplicate by account and thread, and paginate relevant searches. Briefing item caps limit presentation, not inspection. If coverage must be bounded, state the actual range and remaining limitations; do not call a partial scan a complete review. Do not advance a successful-review checkpoint over an unreviewed interval or a failed account.

Read the full available conversation, including the user's sent replies, before treating anything as unanswered or actionable. Thread tools may return only the most recent messages: increase limits or retrieve individual messages where supported. If history remains truncated, disclose it and withhold conclusions or mutations dependent on missing context. Read attachments only when relevant to a decision. Search snippets alone are not evidence of a commitment or deadline.

Preserve the existing minimal model: Inbox means new or unresolved; Action means the user must do something; Waiting means the user has acted and awaits a response/outcome; Later means deliberately deferred; Reference means useful processed mail; Starred means exceptional immediate priority. Discover actual label IDs independently in each account. Missing labels are a limitation or a separate creation proposal, never permission to invent a new structure. Show existing labels separately from proposed additions/removals. A recommendation to archive processed mail and mark it read must name both effects for approval.

Existing filters already handle some newsletters and notifications. Check their observable effects and respect their labels; do not assume a particular filter count or pretend filter definitions are accessible. Avoid duplicate filter suggestions and resurfacing already handled mail. Do not repeatedly present an unchanged skipped recommendation within the conversation; across chats, disclose when review history is unavailable rather than inventing recall. A meaningful reply or changed deadline can justify resurfacing.

Prioritise verified deadlines, personal/family correspondence, decisions and replies, concrete recruitment steps, financial actions, security alerts requiring investigation, bookings/deliveries needing intervention, and genuine engineering project issues. Deprioritise newsletters, promotions, confirmations, ordinary receipts, routine updates, duplicate automated alerts, and historical events. Marketing urgency is not a deadline. A security alert is not automatically malicious: explain the evidence that needs checking and recommend the known official account/site when relevant.

Use source-returned conversation URLs where available. Otherwise construct an account-scoped Gmail conversation link only from verified account identity and a real supported thread identifier; never guess numeric account slots, fabricate identifiers, or relabel a search URL as a direct conversation link. If a direct link cannot be established, identify the thread and disclose the limitation.

## Decisions and execution

Prepare the work before seeking approval. In conversation context, keep each proposal associated with the account identity, current connector account ID, thread/message IDs, observed latest message, proposed label additions/removals, read/star effects, and any draft recipients/subject/body/attachments. A numbered decision refers to this exact proposal, not a fresh open-ended search. Do not persist this map into the installed bundle.

Present only decisions worth the user's attention. A cleanup batch enumerates every included conversation and exact effects before approval; do not use a changing “all matching messages” set. Group similar low-risk changes per account, and keep sending separate from cleanup. Avoid redundant “keep in Inbox” confirmations when no change is needed.

Use an input tool explicitly documented to accept approvals. In this Codex host, `request_user_input_async` can request approval; `request_user_input` is restricted to optional clarification and must not be used for permission. Do not assume tool names or availability transfer to other hosts. A highlighted default is not a submitted answer. While approval is pending, no dependent mutation may run. End the current response after presenting the concrete choices when no independent work remains; resume on the user's answer without issuing the same question again.

If interactive input is unavailable, use the host's supported clickable follow-up actions, with prompts that spell out the account, exact proposal, and authorised effects. In Codex a follow-up can use `- :codex-followup[Archive these two conversations]{prompt="Approve proposal 2 for the named account and two listed conversations: archive only, preserving labels, stars, and read state."}`. Only a follow-up actually submitted by the user grants authority. Otherwise offer a short numbered list accepting “Apply 1; revise 2; skip 3”. Ordinary Markdown checkboxes are visual reminders, not actionable controls. Never claim a control was displayed if the host did not render it.

A direct instruction such as “Archive these two” already authorises that narrow action after current-state verification; do not demand another click. “Draft a reply” permits preparing text in chat. Save to Gmail only when requested or approved. Before drafting as the user, read their voice profile at the path supplied by current personal instructions; if unavailable, disclose that and use a neutral register based only on known facts. A send approval must cover the final body, exact To/Cc/Bcc recipients, attachments, account, and reply/forward context. Revising any material send detail requires renewed approval of the changed message. Never send merely because a draft was approved for saving.

Re-read every approved thread immediately before mutation and compare the proposal's assumptions. If a new message or user action materially changes the plan, skip that item, explain what changed, and prepare a new proposal; unaffected approved items can continue. Already-completed effects are no-ops, not reasons to repeat or broaden a write.

Respect connector units: archive tools may affect a whole thread, while label mutation tools may take message IDs. Enumerate the messages in the approved scope; use IDs of the right type and the right account. Do not use convenience tools that silently create missing labels. Archive alone removes Inbox membership; it does not imply marking read, removing Action/Waiting, or changing stars. If proposing “Action + archive + mark read”, describe all three effects explicitly. Verify the label step before archiving so partial failure does not hide the item without its intended organisation.

After a write, re-read affected state. Check label/read/star outcomes on the intended messages, Inbox removal across the approved thread, and saved draft metadata/content as appropriate. Report partial failures explicitly. For uncertain write responses, inspect current state before retrying; never blindly retry a send or draft creation. Report a send as verified only when provider evidence supports it. If the connector cannot perform an approved action, say so and give the precise manual step without claiming completion.

No real mailbox reads or writes are needed to install or evaluate this skill. Use synthetic scenarios for behavioural checks; account integration and actual UI behaviour require a separately invoked live review.
