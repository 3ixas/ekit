# Review workflow

The user chooses each task disposition and final working time. Use the `grilling` skill as a supporting questioning method, adapted for operational planning:

- Investigate available facts first. Form a decision frontier: questions whose answers do not depend on other unresolved questions. Ask these together in a numbered round, grouped by a useful theme and ordered by urgency. Use a short title and a concrete recommendation or options for each where evidence supports one; ask open questions when the answer cannot be inferred.
- Keep rounds readable and proportionate to the actual choices; if the frontier is large, divide it into manageable themed rounds while keeping the remaining items visible and advancing through them. Do not turn the full task inventory into a questionnaire or force a recommendation for an unknown fact.
- Wait for the user's answers, apply and verify specific decisions they have already authorised, then use those answers to form the next round. Dependent timing and capacity choices belong in a later round; do not guess or force a full-session approval gate before making already agreed changes. If the user prefers one question at a time or changes the pace, follow that preference.
- End with a concise agreed plan, what was deferred or remains unresolved, and any evidence gaps. Do not repeat requests for approval, invent decisions, or send messages. The full-coverage, pending-queue, recurrence and deadline rules below remain in force.

## Load and check coverage

1. Read the vault's live instructions/configuration, Goals Home, operating manual, current weekly plan and relevant confirmed review. Resolve the current task authority and fixed-calendar sources from the live vault configuration. Todoist is the current task authority; preserve the legacy FlowSavvy source and do not disable it or change integrations merely because authority changed. If provider records conflict, disclose the scope and any coverage gap.
2. With the Todoist connector, discover current user, projects, sections, active tasks, labels and account timezone. Page every result. Include Inbox, all active projects, their tasks and subtasks, including unscheduled, exploration, deferred and waiting work. Follow parent-specific pagination where a broad query does not prove child coverage. Archived/completed objects are not active work, but completion history is relevant evidence. Build a temporary in-memory inventory; do not copy task descriptions, credentials or employer information into the skill or private state.
3. Read the current weekly selection, overdue/due-today/tomorrow tasks, real deadlines and relevant bounded calendar commitments. Resolve the calendar registry live; distinguish fixed events from task mirrors, compare IDs to avoid double counting, and do not assume an imported mirror or disabled source is authoritative. Retrieve the user's own completion and update activity with the user ID and an inclusive start/exclusive end in the user's timezone; paginate. Use completion events for recurring occurrences. Note provider retention, missing pages or inaccessible integrations.
4. Report counts of projects/tasks scanned, outstanding decisions and any coverage gaps. A full scan is not a claim that every item was acted on. Do not infer progress from a calendar block, a missing task or an elapsed time.

## Daily review and next day

Compare the day's agreed snapshot, live tasks, relevant calendar, completion events and change history. Account for each planned item, including one rescheduled during the day if history supports it. The snapshot is a baseline of agreed IDs and times, not a complete immutable history: later manual edits and missing events may prevent reconstruction. If no baseline exists, say so and use available evidence without inventing the original plan. If a task is unchecked, ask about actual work rather than assuming failure; preserve partial progress and a useful next action.

Report the outcome of every prior-plan item, including verified completions and moves. Walk through each item that needs a decision: completed, continue, move to an agreed time, defer until a chosen trigger, or retain without a working date. Prioritise immediate deadlines and obligations; also bring up eligible older items rather than allowing lower-priority work to starve. Persist the IDs of items needing decisions or verified follow-up in the private pending queue before discussing them. Keep each ID queued until the user decides and any requested write is read back successfully. Rebuild details from live Todoist; if a session or write is interrupted, reload the queue, re-read tasks and history, and disclose unresolved items. Recover agreed actions from conversation when available; if unavailable, ask what to do rather than invent the lost decision or repeat an uncertain write. Do not silently carry tasks to tomorrow.

Propose a feasible next-day plan using the user's priorities, requested duration and known commitments. Surface conflicts and trade-offs; the user chooses the final times and can adjust them. Show a concise account of what's selected, intentionally deferred and unresolved. Apply decisions already made as the user requests; do not insist on a second approval for the same change.

## Weekly review

Scan every active task and project, including deferred and exploratory work, as above. Walk through items with an upcoming deadline, overdue work, unfinished weekly selections, blockers, unclear commitments, changed circumstances or age-review triggers. Discuss independent decisions in focused rounds as above. Record the outcome for the week's chosen work, genuine obligations, standing practices and deliberate trade-offs in one short weekly note. No task becomes active just because it was scanned or appears in a life area.

## Age and waiting rules

An open one-off task is eligible when 30 full calendar days have elapsed since its last actual user review, or, if never reviewed, its earliest reliably verified creation date. A scan, recommendation, mere listing, or unanswered question does not reset the clock. A user decision to retain, defer, schedule or otherwise change a task counts as a review; record the ID and local review date. Resolve a queued item only after any requested change is verified. If a task has a known future blocker or return date, keep it in the scan but respect the trigger until it arrives or becomes questionable; an unknown blocker is a question, not a reason to hide it indefinitely. Recurring obligations stay in the daily/weekly due and completion review; do not treat every occurrence as a stale one-off.

Todoist `addedAt` can be the migration date, not the age of the underlying idea. Consult any `planning_workflow.creation_provenance` paths in the live vault config. Where an existing private migration map explicitly identifies the same current task and an earlier valid source creation date, use the earliest defensible date with its provenance; do not infer matches by title. Otherwise use Todoist's timestamp as the earliest known date and disclose that older history may be missing. Missing, malformed or future dates are unknown, not new tasks. Do not reset the age clock during setup. Stale items that cannot be discussed today remain visible in the decision queue at the next session.

## Apply and verify

Use live task IDs, retrieve affected objects immediately before writing, and send only changed fields. Compare labels as unordered sets and preserve descriptions, parents, durations, dates and deadlines unless the user explicitly changes them. For a recurring task's occurrence, use Todoist's recurrence-preserving rescheduling operation, check its scope and read back the occurrence and series. Avoid replacing a recurring due string to move one occurrence. Never complete a task merely to advance a repeat. Confirm actual completion with the user or reliable occurrence-specific activity before marking anything complete.

Before setting a time, check available commitments and overlap. Use the user's confirmed time and timezone; handle genuine deadline separately from a working date. Reuse an existing task/session instead of creating duplicates; a session completion is distinct from completion of its wider project. For new creates or uncertain tool results, search/read back before retrying. A direct Todoist/calendar integration should produce one representation; do not add another event unless the user requests it. If a write fails or its result is uncertain, report the particular item and keep its ID pending. After each verified day-plan change, update the private snapshot as partial; mark it complete only when the agreed day plan is fully applied and checked.
