# Refresh existing codebase research

Use when the user asks to deepen, verify, refresh, or correct an existing codebase research document. This mode explains current code; planning-document critique belongs to `doc-review`, and unexpected behaviour with an unknown cause belongs to `debug`.

1. **Read the scoped document and its evidence.** Discover the document from the request and project conventions. Read it whole, including linked evidence relevant to its claims; inspect current repository instructions and revision. If several documents are equally plausible, ask which one. Read prior decisions only when needed to interpret the research; do not treat a desired change in a ticket as evidence of current behaviour.
2. **Choose investigation targets.** Identify thin sections, unexplained connections, unsupported claims, stale references, and open questions answerable from code or primary dependency sources. Keep targets within the original research question. Prioritize claims whose accuracy changes the explanation rather than adding detail everywhere.
3. **Trace and verify.** Follow actual entrypoints, callers, data transformations, state, and dependencies. Read the implementation instead of inferring behaviour from names or tests alone. Verify paths, symbols, and behaviour; include current file/line references and revision-pinned links where available. Use the existing complexity-based exploration approach only when independent angles justify it. Verify external API claims against the project's installed version and current primary sources.
4. **Update within authority.** When document editing is authorized, correct claims and deepen relevant sections in place, preserving the original scope, frontmatter, useful structure, and resolved decisions. If ownership or edit authority is absent, return proposed corrections instead. Remove answered open questions and record genuinely unresolved ones with what was checked. A failed lookup alone does not prove a feature is absent. Mark contradictions with prior decisions for review rather than rewriting those decisions. Do not introduce requirements, architecture proposals, automatic splitting, or new artifact locations.
5. **Show the improvement.** Report which claims were corrected or verified, which connections gained evidence, which questions were answered, and what remains uncertain. Distinguish observed behaviour from inference and unavailable evidence. Stop when the selected gaps are resolved or have concrete blockers; length is not a completion criterion.

Method adapted independently from HumanLayer's pinned `grind-research`; exact provenance and adaptation boundaries are in this bundle's metadata.
